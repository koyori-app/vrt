# ジョブワーカーの分離と停止検知

`apps/backend` の API プロセスは、HTTP を提供しながら apalis のワーカーを 3 本抱えている。
このワーカーが止まっても、プロセスは生きたまま HTTP を返し続ける。
2026-08-27 の障害では、その状態が 4 時間以上続き、ビルドが 20 件「処理中」のまま滞留した。
この文書は、ワーカーを独立プロセスへ移して、止まったときに自力で復帰させるための設計を定める。

## 起きたこと

Postgres が WAL の同期に失敗して異常終了した。

```
2026-08-27 16:24:31.632 UTC [4580] PANIC:  could not fdatasync file "0000000100000000000000AE": Input/output error
2026-08-27 16:24:55.463 UTC [1] LOG:  all server processes terminated; reinitializing
2026-08-27 16:30:25.433 UTC [1] LOG:  database system is ready to accept connections
```

Postgres 自体は 6 分弱で復旧し、以後 PANIC は再発していない。
復旧しなかったのは API プロセスのワーカーのほうである。

`apalis.workers` のハートビートは、`compare_build` と `github_status` と `github_webhook` の 3 本だけが 16:23:37 から更新されず、調査時点で 4 時間 43 分古かった。
その結果 `compare_build` のジョブが 20 件、`github_status` が 25 件、いずれも `attempts=0` で積み上がった。
一度も取得されていないので、ロック解除もリトライも働かない。
レンダリングは別プロセスの runner が担当しているため最後まで完走し、比較だけが実行されないビルドが並んだ。

同じ瞬間に接続を失った runner は復帰している。
`RestartCount=2`、起動時刻は Postgres の復旧と同じ 16:30 である。
API プロセスは `RestartCount=0` で、一度も再起動していない。

## 止まったワーカーは終了していた

apalis のワーカーは、ハートビートに失敗した時点で走行ループを抜ける。

```rust
// apalis-core-1.0.0-rc.9/src/worker/mod.rs
Err(e) => Err(WorkerError::HeartbeatError(e.into())),   // 403 行
...
Err(WorkerError::GracefulExit) => return Ok(()),        // 243 行
Err(e) => return Err(e),                                 // 244 行
```

`GracefulExit` 以外の失敗はそのまま戻り値になるので、接続を失ったワーカーのタスクは即座に終了する。
つまり今回は「生きたまま取得を止めた」のではなく、3 本とも終了していた。
runner が復帰したのは、その終了を `supervise_worker` が捕まえて非ゼロ終了したからである。

API プロセスにはこの監視がない。
ワーカーは `tokio::spawn` で起動されるだけで、`JoinHandle` を待つのは HTTP サーバーが終わったあと、つまり停止処理のときだけである。

```rust
// apps/backend/src/server.rs
for (label, handle) in worker_handles {
    match handle.await {
        Ok(Ok(())) => info!("{label} worker stopped"),
```

途中でタスクが終わってもこの `for` には到達しない。
ログも出ず、再起動もされない。

死活監視も助けにならない。
Compose のヘルスチェックは 3400 番への TCP 接続だけを見ているため、HTTP が生きている限り healthy と報告される。

## なぜ分離するか

API プロセスの中でワーカーを監視して、止まったらプロセスごと落とす作りにもできる。
ただしその場合、`compare_build` のワーカーが死んだだけで HTTP も巻き添えになる。
CLI からのアップロードを受け付けている最中の再起動は、ビルドの投入そのものを失敗させる。

ワーカーを独立プロセスへ移せば、再起動の影響がキューの中だけに閉じる。
復帰の仕組みは runner が実証済みで、`supervise_worker` と restart policy をそのまま流用できる。
API 側は投入だけを担うので、ワーカーの生死と HTTP の可用性が切り離される。

分離すると渡す秘密情報も減る。
3 本のワーカーが実際に読むのは次だけである。

- **compare_build**：DB、成果物ストレージ、`storage_min_retention_days`、`github_status` キューへの投入
- **github_status**：DB、Redis（インストールトークンのキャッシュ）、HTTP クライアント、`app_url`、GitHub API のベース URL、GitHub App の資格情報
- **github_webhook**：DB のみ

`PERSONAL_TOKEN_SECRET`、`OAUTH_TOKEN_ENCRYPTION_KEY`、OAuth クライアントの資格情報は、いずれのワーカーも使わない。
runner に渡す設定を絞ったのと同じ考え方で、新しいプロセスにも必要な分だけ渡す。

ただし現行の `JobState` は `Settings` を丸ごと持ち、`Settings` は上記の秘密情報を必須として検証する。
そのまま流用すると、使わない秘密情報を渡さなければ起動できない。
`RenderJobState` と同じように、新しいプロセス用の state を専用に組み、`app_url` や GitHub App の資格情報は個別のフィールドとして渡す。
この組み替えも本設計の作業範囲に含める。

## 方針

### ジョブワーカーを独立プロセスへ移す

`vrt-runner` と同じ形の実行ファイルを 1 つ足し、3 本のワーカーをそこで動かす。
Compose には対応するサービスを 1 つ追加する。

API プロセスは投入専用にする。
ワーカーを起動するかどうかは環境変数で切り替え、既定は従来どおり起動する側に倒す。
開発用の単一コンテナ構成をそのまま動かせるようにするためで、本番ではこれを無効にする。

API 側でワーカーを起動する構成を選んだ場合も、同じ監視を通す。
その構成ではワーカーの死が HTTP の再起動を意味するが、無言で滞留するよりは短い停止のほうが軽い。

### タスクの終了を一次の検知にする

`supervise_worker` を共有の場所へ移し、ワーカーを抱えるプロセスはすべてこれを通す。
いずれかのワーカーのタスクが終了したら、キュー名と理由をログに出し、非ゼロで終了する。
今回の止まり方はこの経路で即座に捕まる。

停止処理との区別は `watch` の受信側で行う。
シャットダウンが要求されている場合、ワーカーの終了は正常な完了として扱い、終了コードは 0 にする。

DB へ接続できない間は、この一次検知が発火し続ける。
ワーカーはハートビートの失敗で終了するので、DB 断中のワーカープロセスは再起動を繰り返す。
これは許容する挙動である。
restart policy のバックオフが間隔を空け、DB が戻れば次の起動で復帰する。
今回の障害でも runner はこの形で 2 回再起動して復帰した。

プロセス内でワーカーを起動し直す案は採らない。
接続プールは sqlx が再接続するので起動し直すこと自体は成り立つが、復帰の経路が runner と二本立てになる。
プロセスを終えて restart policy に委ねれば、一時ファイルや外部プロセスの後始末もまとめてやり直せる。

### ハートビートは二次の検知に使う

タスクが終了しない止まり方が残る可能性は消せない。
そのため、自分のワーカーのハートビートが古くなった場合も終了条件に加える。

判定は、**このプロセスが登録したワーカー ID** に対してのみ行う。
`apalis.workers` の行はワーカー ID ごとに `INSERT` され、vendor 内に削除する経路がない。
ワーカー ID は起動のたびに新しく生成されるので、キュー名で引くと過去のプロセスが残した行が必ずヒットする。
キュー単位で判定すると、起動直後から常に「古い」と判定されて再起動を繰り返す。
同じキューを複数のプロセスが持つ構成では、他プロセスの新しいハートビートに隠れて自分の停止を見落とす逆向きの誤りも起きる。

古さは DB の `NOW()` との差で測る。
アプリ側の時刻と比べると、コンテナと DB の時計のずれがそのまま誤検知になる。

閾値は 3 分とし、環境変数で変えられるようにする。
ハートビートの間隔は 30 秒なので、6 回分の欠落にあたる。
これより長い値を選ぶ理由は薄い。
Postgres の復旧に 6 分弱かかったことは閾値を大きくする根拠にならず、必要なのは次の 2 つの猶予である。

- 監視タスクは、DB へ接続できないことを理由にハートビートを「古い」と判定しない
- 再接続してから最初のハートビートが書かれるまで、判定を待つ

この 2 つはハートビート判定の話であって、一次検知には適用しない。
DB 断中のプロセス終了は前節のとおりワーカー終了の経路で起き、それで正しい。

起動直後に自分のワーカー行が存在しない状態も、同じ猶予の中では正常とみなす。
ただし猶予を過ぎても行が現れない場合は異常として終了する。
登録の失敗自体は poll ストリームの先頭で起きてワーカータスクを終了させるため、一次検知で捕まる。
この条件はそれとは別の、行が現れないままタスクだけ生き続ける未知の止まり方への保険である。

### 滞留は監視に出すが、自動終了の根拠にしない

ハートビートはジョブの進捗を表さない。
ハートビートと取得は別のストリームで、同時実行数が長時間かかるジョブで埋まった場合、取得だけが止まってもハートビートは進む。
この状態は今回と同じ症状を生むが、上の 2 つの検知では捕まらない。

そのため、キューごとの滞留を数値として外に出す。
API に読み取り専用のエンドポイントを足し、キューごとのワーカー数、最新ハートビートの古さ、`attempts=0` の Pending 件数、その最古の待ち時間を返す。

この値でプロセスを終了させることはしない。
滞留は「ワーカーが詰まっている」場合と「単に混んでいる」場合を区別できず、混雑を障害と誤認して再起動すると滞留をさらに悪化させる。
判断は人と外形監視に残す。

エンドポイントは認証不要とする。
外形監視はセッションを持てないためで、その代わりワーカー ID や接続情報は返さず、集計値だけを返す。
既存の `/health` は認証不要のまま、プロセスの死活だけを表すものとして変えない。
コンテナのヘルスチェックも切り替えない。
切り替えるとコンテナの生死が Postgres の可用性に従属し、DB 障害のたびに再起動が始まる。

### 再起動の代償を認めておく

ワーカープロセスを落とすと、実行中のジョブは `Running` のまま残る。
これは 300 秒後に孤児として再投入され、そのとき `attempts` が 1 増える。
`compare_build` の上限は 3 回なので、短い間隔で再起動が続くとリトライ枠を使い切って Failed に落ちる。

停止時は在庫を捌いてから終わるように、猶予期間を設ける。
runner は 1 時間だが、比較は数分で終わるので 10 分とする。

### 異常終了へ向かう待ちには期限を切る

停止時にワーカーの走行ループが返るのは、apalis が in-flight のジョブを終えてからである。
apalis の停止には停止タイムアウトが無い（`WorkerContext` は「shut down and all tasks have completed」で解決する）。

そのため、異常検知後に残りのタスクを無期限で待つと、戻ってこないジョブが 1 本あるだけで非ゼロ終了に到達できない。
`restart: unless-stopped` はプロセスが終了しないと発火せず、worker と runner のコンテナには healthcheck も無いので、外から異常と判定して落とす経路も無い。
「1 本が死に、別の 1 本が hung」という複合状況で、復帰機構そのものが止まり、この文書が無くそうとした「HTTP は正常なのにキューだけ死ぬ」状態へ戻ってしまう。
しかも hung は仮定の話ではない——同時実行数が hung ジョブで埋まる状態は、`/v1/health/queues` が可視化しようとしている状態そのものである。

そこで**異常経路の待ちにだけ 60 秒の期限**を置き、期限切れでも待っていたタスクを名指ししてから非ゼロで終える（`supervision::DRAIN_DEADLINE`）。
取り残した実行中ジョブは `Running` のまま 300 秒後に孤児として再投入されるので、失われはしない——上に書いた再起動の代償と同じ枠組みで、`attempts` を 1 消費する。

正常な停止（停止要求が先に来た場合）には期限を掛けない。
在庫を捌く猶予は `stop_grace_period` が持っており、そこを縮めるとデプロイのたびに進行中のジョブを捨てることになる。

## 受け入れ条件

- ワーカーのタスクが終了した場合、プロセスは非ゼロで終了する。ログにキュー名と理由が残る
- 残ったワーカーが戻ってこないジョブを抱えていても、待ちを 60 秒で打ち切って非ゼロで終了する。諦めた相手はログに名前が残る
- 自分が登録したワーカーのハートビートが閾値を超えて古い場合、非ゼロで終了する
- 同じキューに過去のプロセスの古い行が残っていても、自分のワーカーが健全なら終了しない
- 同じキューを他のプロセスが健全に処理していても、自分のワーカーが古ければ終了する
- 監視タスクは、DB へ接続できないことを理由にハートビートを「古い」と判定しない（DB 断中のワーカー終了による再起動は許容する）
- 新しいワーカープロセスは、OAuth とパーソナルトークン系の環境変数なしで起動できる
- 起動猶予を過ぎても自分のワーカー行が現れない場合は終了する
- シャットダウンが要求されている間は、ワーカーの終了もハートビートの古さも終了要因にしない。終了コードは 0 になる
- 監視タスク自身が落ちた場合、監視が無言で消えず、同じ終了経路に入る
- 監視エンドポイントは、キューごとのワーカー数、ハートビートの古さ、`attempts=0` の Pending 件数、最古の待ち時間を返す

テストでは次を確認する。

- 閾値の境界だけでなく、明確に下回る値と上回る値の両方を通す
- 3 本のうち 1 本だけが古い場合も終了する
- ハートビートの取得が失敗した場合に終了しない
- シャットダウン送信後にワーカーが正常終了しても、終了コードが 0 になる
- 古いハートビートが残った状態で再接続の猶予内なら終了しない（DB 断ではワーカー自体が終了するため実環境ではほぼ作れない状態であり、監視タスク単体のテストとして確認する）

## 切り替えの順序

API 側でワーカーを止める設定と、新しいワーカーサービスの追加は、同時に反映する必要がある。
先に API を無効にすると、その時点から誰もキューを消費しなくなる。
本番へは、ワーカーサービスを起動して登録を確認してから、API の設定を切り替える。

## 扱わないこと

Postgres が `fdatasync` に失敗した原因そのものは、この設計の対象外である。
ディスクの健全性は別に確認する必要がある。
この設計が保証するのは、同じことが再び起きたときに滞留が数分で解消することであって、障害を防ぐことではない。

終わらないジョブが同時実行数を埋め尽くす詰まり方は、この設計では自動復帰しない。
ハートビートは正常なまま取得だけが止まるため、滞留メトリクスとして見えるだけである。
必要になった時点で、ジョブ単位のタイムアウト層を別に検討する。

滞留したビルドの回収も対象外とする。
今回のジョブは `attempts=0` の Pending として残っており、ワーカーが復帰すればそのまま取得される。
ジョブ自体が失われる経路が見つかった時点で、別に検討する。
